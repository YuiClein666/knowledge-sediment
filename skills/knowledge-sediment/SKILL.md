# Knowledge Sediment · 知识沉淀

> 把**工作中产生的可复用知识**沉淀下来，而不是只记录"用户是谁"。
> 本 skill 管的是**知识资产**（我会什么），不是**个人档案**（我是谁）——两者刻意分开。

---

## 一、沉淀什么（判断标准）

**值得沉淀**（三条门禁，任一条满足就该考虑）：

1. **可复用**——换个项目/场景还能用上（技术方案、语法要点、配置方法）
2. **有因果**——不只说"怎么做"，还说"为什么这样做 / 什么条件下成立"
3. **踩过坑**——报错、陷阱、反直觉的发现（**这类价值最高**，因为最难重新推导）

**不值得沉淀**：
- 一次性的、项目特有的细节（除非能提炼出普适教训）
- 纯抄录的文档内容（没有自己的理解）
- 密钥 / 凭据 / 个人隐私（**绝对禁止**，见第八节）

---

## 二、沉淀到哪（★ 读配置，不要凭记忆猜）

> **每个知识库的分类都不同**——所以**不要**假设存在某个固定单元。
> 先读配置，再决定放哪。

### 怎么读

```bash
python "<工具库>/scripts/config.py"          # 打印配置位置与分类清单
```

或直接读配置里的 `taxonomy`：

```json
{
  "taxonomy": {
    "categories": [
      {
        "id": "10-xxx",
        "title": "分类名",
        "keywords": ["关键词1", "关键词2"],
        "units": [
          {"id": "11-yyy", "title": "单元名", "keywords": ["关键词1", "关键词2"],
           "summary": "这个单元收什么"}
        ]
      }
    ]
  }
}
```

配置默认在 `~/.knowledge-sediment/config.json`（可用 `KNOWLEDGE_SEDIMENT_CONFIG` 覆盖）。

### 匹配规则（按优先级）

| 情况 | 动作 |
|---|---|
| 命中某个**单元**的 keywords | 写入该单元 |
| 命中某个**分类**的 keywords，但没命中具体单元 | 写入该分类下最接近的单元；若都不合适，**建议新建单元**并说明理由 |
| 都不命中 | 落 `00-inbox/`，并在回复里明说"这条我放 inbox 了，你看该归哪" |
| 配置文件读不到 | 同上，落 `00-inbox/`，**不要虚构分类** |

### 为什么不能猜

写错位置比不写更糟——它会污染别的单元、稀释检索准确度，
而且这种错误很难被发现（内容在不该在的地方，检索时命中率变低，但没人知道为什么）。

**不确定就落 inbox。** inbox 是缓冲区，不是垃圾桶——但要定期清理，不要让它变成永久的垃圾场。

## 三、入库前的功课（★ 决定沉淀质量的关键，不要跳）

> **沉淀不是"提取"，是"编辑"。**
> 把会话内容整理成文档直接入库，会把"没讲透的、当时答错的、和已有内容打架的"
> 一起固化进去——**三个月后你自己都不敢信它**。

### 为什么必须先了解这块知识

| 场景 | 直接提取的后果 |
|---|---|
| 会话里**没讲透** | 半成品被固化，将来还要重学一遍 |
| 会话里的结论**本身不准** | 错误被固化——**比没记更糟**，因为你会以为自己知道 |
| 只检查"有没有同名文件" | 漏掉命名不同但实际相关的内容 → 重复或互相矛盾 |

### 功课清单（按内容价值分级执行）

| 步骤 | 做什么 | 轻量 | 标准 | 深度 |
|---|---|:--:|:--:|:--:|
| ① **界定主题** | 一句话说清核心命题（避免把"现象"当"结论"） | ✓ | ✓ | ✓ |
| ② **查已有** | 不只看同名——按 keywords + relations 找**所有相关的** | ✓ | ✓ | ✓ |
| ③ **找缺口** | "这个话题应该包含什么" vs "已有 + 本次覆盖了什么" | | ✓ | ✓ |
| ④ **验证** | 会话里的说法可靠吗？有来源吗？和已有内容冲突吗？ | | ✓ | ✓ |
| ⑤ **定位** | 按 taxonomy 找单元，按 relations 找上下游（避免成为孤岛） | ✓ | ✓ | ✓ |
| ⑥ **决定动作** | 新建 / 补全 / 合并 / 修正 / 标注矛盾 | | ✓ | ✓ |
| ⑦ **标注** | 哪些确定、哪些不确定（**写清具体位置**） | | ✓ | ✓ |

**分级判据**：

- **轻量**：明确事实（一行能说完，如某个命令的用法）
- **标准**：有因果的技术点（"为什么这样做、什么条件下成立"）
- **深度**：有争议、有陷阱、**可能与已有内容冲突**的

> 不是所有沉淀都值得做功课；但**值得建单元的内容一定值得**。

### ③ 找缺口是最关键的一步

它要求你知道"**这个知识点应该长什么样**"——而这通常是当前会话里**没有**的信息。

做法：**把话题拆成几个必答问题**，看已有内容 + 本次会话覆盖了几个。

例：沉淀 MVCC 时，必答问题至少包括

- MVCC 解决什么问题
- 版本链怎么组织（undo log / 事务 id）
- **RR 和 RC 下 read view 的生成时机有什么不同**
- 快照读与当前读的区别

如果会话只讲了前两条 → 缺口在第 3、4 条 → **要么补课，要么明确标注**。

### ★ 一个可操作的自测判据

"了解够不够"是模糊的，把它变成一句话的检查：

> **"如果用户现在追问 X，我能答上来吗？"**

答不上 → 说明没讲透 → 要么补课，要么在文中标 `confidence: low` 并写清**哪里不确定**。

这比"我觉得我懂了"可靠得多，而且不需要任何额外工具。

### 但不要越界

做功课 ≠ 把话题写成教科书。**边界是：让这条记录自包含、可独立理解。**

判据：

> **只看这条记录、看不到原对话，还能复现当时的理解吗？**
> 能 → 够了。不能 → 补到能为止。

### 当功课做不全时（内部资料 / 用户口述）

上面七步有个前提：**agent 能独立获取这块知识**（公开知识、查得到、验得了）。

但有一类内容拿不到——**企业内部资料、私有系统、需要特定权限才能访问的文档**。
更常见的是：**用户自己口述了答案，但 agent 无法验证**（判断不了对错、全不全、
和内部其他资料是否冲突）。

> 注意：**入库内容的来源不必是 agent 检索到的**，可以是用户口述的、粘贴的文档。
> agent 的角色是**编辑**（把内容整理成合格的知识条目），不是搬运工。

这类内容**照样要入库**（它们往往最有用），只是功课换成三个替代动作：

| # | 动作 | 说明 |
|---|---|---|
| ① | **先问：有可访问的资源吗？** | 内部文档 / 知识库 / MCP 连接器——**有时用户手里真有**。这是"能力发现"，比闷头写或直接放弃都好 |
| ② | **标注来源 + 标明未验证** | `source: 用户口述` 或 `source: 内部文档`，并把 `confidence` 降一档 |
| ③ | ★ **留下验证路径** | 把"我验证不了"变成"**要验证它需要什么**" |

第 ③ 个是这类内容的价值所在——**必须写具体**，例如：

    ## 未验证的部分
    - 本文来自用户口述，未经独立验证
    - 要验证需要：查内部 XX 平台文档 / 找 XX 确认第 2 节的顺序
    - 若后续拿到内部资料，优先核对"鉴权顺序"这一节

**这样同时做到三件事**：诚实（读者知道可信度）、可延续（下次有资料时知道该验什么）、
不阻塞（不会因为"验不了"就不入库）。

**这类内容的判据换了一个**：

> 不是"**验证得了吗**"，而是"**读者知道该不该信吗**"。
>
> 验证不了但标清楚 → **有用**；验证不了却装作确定 → **有害**。

## 四、写入格式

```markdown
---
title: "<断言式标题——'B+树让范围查询更高效' 优于 '索引介绍'>"
type: note
tags: [标签1, 标签2]
source: <来源：项目实践 / 学习笔记 / 复盘 / 用户口述 / 内部文档>
visibility: public | internal   # internal = 含内部或私有信息，导出公开版时应被过滤
created: YYYY-MM-DD
updated: YYYY-MM-DD
confidence: high | medium | low
status: draft
relations:
  - type: relates_to          # requires | relates_to | supersedes | contradicts | used_in
    target: <目标单元或文件路径>
---

# <标题>

## 结论
（先给结论，再展开）

## 细节
（做法、原理、例子）

## 不确定的地方
（只写确实不确定的具体点，并说明"下次怎么验证它"。
  这一节不是必须的，但**有不确定却什么都不写，是更糟的选择**）

## 相关
（关联的其他单元）
```

### 四条硬要求

1. **标题成断言**——"X 导致 Y"优于"关于 X"。这是**对检索帮助最大**的一条，也最容易被忽略。
2. **先结论后细节**——让人和 AI 都能快速判断是否相关。
3. **标 `source` 和 `confidence`**——读者需要知道可信度。
4. **`status` 从 `draft` 开始**——不要把没验证的东西标成 `promoted`。
5. **标 `visibility`**——`internal` = 含内部或私有信息。
   **知识库将来若要导出公开版，`internal` 的内容应被自动过滤**（而不是靠人肉记得）。
   内部资料、公司系统名、未公开流程一律标 `internal`。

## 五、质量门控（三级路由）

| 层级 | 条件 | 处理 |
|---|---|---|
| **Tier 1** | 有明确证据/来源、表述完整、可独立理解 | 直接写单元目录，`status: promoted` |
| **Tier 2** | 有价值但**某处不确定** | 写入，并在文中**标出不确定的具体位置**（不是笼统写"不确定"） |
| **Tier 3** | 低置信度 / 依赖主观判断 | 只写 `00-inbox/`，`status: draft`，等后续验证 |

**关键原则**：只让 AI 判**可对照的判据**（有无来源、是否完整、能否独立理解），
**不让 AI 判"有没有价值"**——研究显示通用 LLM 打"质量分"会系统性偏宽松、偏袒文笔好的内容。

> Tier 2 的意义：**允许"不完整"入库，但必须留锚点。**
> 标了不确定 → 后续补全是**预期内的**（不算返工）；没标却错了 → 那才是真的返工。

## 六、生命周期（晋升制）

```
draft（草稿，在 inbox）
  ↓ 被引用 / 被检索命中并实际使用 / 同类模式重复出现
promoted（晋升为正式知识）
  ↓ 过时 / 被新方案取代
deprecated（废弃，移入 90-archive）
```

**晋升依据必须是可观测的**，不依赖主观判断：

- 出现在其他笔记的 `relations` 里（被引用）
- 被检索命中并实际用于解决问题
- 同类内容多次出现（说明是通用模式，不是个例）

**修改时要记录原因**（后续会用这些数据算指标）：

| 原因 | 含义 | 性质 |
|---|---|---|
| `correct` | 之前写错了 | 否定过去 |
| `complete` | 之前漏了关键的 | 否定过去 |
| `clarify` | 之前有歧义 | 否定过去 |
| `extend` | 增加了新维度 | 知识生长 |
| `update` | 外部事实变了 | 知识生长 |
| `supersede` | 被更好的方案替代 | 知识生长 |

> **前三种是"返工"，后三种是"长大"。** 区分它们，才能判断问题出在"质量"还是"演进"。
> 若一条**已晋升**的内容被 `correct` / `clarify`，那是需要留意的信号——
> 说明当初的验证不够。

## 七、执行流程

```
1. 判断有没有值得沉淀的内容（三条门禁）
   ↓ 有
2. ★ 做功课（见第三节）：界定主题 → 查已有 → 找缺口 → 验证 → 定位
   ↓ 自测："如果用户追问 X，我能答上来吗？"
   ↓ 答不上 → 补课，或标 confidence: low + 写清哪里不确定
3. 决定动作：新建 / 补全 / 合并 / 修正 / 标注矛盾
   （已有内容若和新理解冲突 → 标 contradicts，不要直接覆盖）
4. 按第四节格式写入
5. 更新索引：python "<工具库>/scripts/knowledge_cli.py" index
6. ★ 告知用户：「沉淀了什么 / 放在哪 / 置信度 / 哪部分不确定」
7. ★ 记录事件（见下方）
```

**第 6 步不能省。** 用户有权知道你把什么写进了他的知识库、放在了哪里——
他可能不同意这个归类，也可能认为这条根本不值得记。**静默写入会让知识库失去他的信任。**

**第 2 步也不能省。** 跳过它就是把"半成品"当成"成品"存起来——
这是知识库质量问题的**最大来源**，而且事后很难发现。

### 记录事件（让指标有数据）

沉淀 / 修改 / 检索之后**顺手记一笔**。这是唯一需要额外做的事，
但它是所有指标的数据源——**没有它，"这套机制有没有在工作"就只能靠猜。**

    # 沉淀了一条
    python "<工具库>/scripts/knowledge_cli.py" log --type sediment --file "<相对路径>"

    # 修改了已有内容（★ --reason 必填）
    python "<工具库>/scripts/knowledge_cli.py" log --type revise --file "<路径>" --reason complete

    # 检索过（命中与否都要记）
    python "<工具库>/scripts/knowledge_cli.py" log --type retrieve --hit yes

`--reason` 的六个合法值，分成性质相反的两类：

| 值 | 含义 | 性质 |
|---|---|---|
| `correct` | 之前写错了 | **否定过去（返工）** |
| `complete` | 之前漏了关键的 | **否定过去（返工）** |
| `clarify` | 之前有歧义 | **否定过去（返工）** |
| `extend` | 增加了新维度 | 知识生长 |
| `update` | 外部事实变了 | 知识生长 |
| `supersede` | 被更好的方案替代 | 知识生长 |

**为什么 reason 必填**：它是区分"质量有问题"和"知识在演进"的唯一依据。
漏标就算不出返工率，也就看不出入库门槛是不是太松。

看指标：

    python "<工具库>/scripts/knowledge_cli.py" metrics
    # → 返工率 / 检索成功率 / 修改原因分布

## 八、禁止事项

- ❌ **绝不沉淀密钥 / 密码 / Token / 个人隐私**（这是红线，没有例外）
- ❌ **绝不沉淀用户所在公司的内部信息**（内部平台名、未公开的战略、客户数据）——
  尤其是知识库会同步到公开仓库的情况下
- ❌ 不沉淀纯抄录内容（无自己的理解）
- ❌ 不重复沉淀（先做第二节的查已有）
- ❌ **不擅自覆盖已有结论**（有冲突应标 `contradicts`，而不是直接改掉）
- ❌ **不在没做功课的情况下写入**（宁可标不确定，也不要假装完整）

## 九、工具命令

> `<工具库>` = 本插件所在目录（clone 下来的仓库路径）。
> `<知识库>` 通常不用指定——装了插件后配置里已记录。

```bash
# 看配置（知识库在哪、有哪些分类）
python "<工具库>/scripts/config.py"

# 重建三层索引（顶层 → 分类 → 单元）
python "<工具库>/scripts/knowledge_cli.py" index

# 生成引用地图（单元之间的关系）
python "<工具库>/scripts/knowledge_cli.py" map

# 生成结构健康度报告（哪里膨胀了该拆）
python "<工具库>/scripts/knowledge_cli.py" health

# 统计概览
python "<工具库>/scripts/knowledge_cli.py" stats

# 沉淀一条到 inbox
python "<工具库>/scripts/knowledge_cli.py" capture --title "标题" --content "内容" --tag "标签"

# 同步（索引重建 + commit，可选 push）
python "<工具库>/scripts/knowledge_cli.py" sync --push

# 在任意工作区开启沉淀目录（创建 .knowledge/）
python "<工具库>/scripts/init_workspace.py" --workdir "<工作区路径>" --kb "<知识库>"
```

所有命令都支持 `--kb` 显式指定知识库位置（优先级最高）。

## 十、它和"个人档案"的区别（不要混）

| | 知识库（本 skill） | 个人档案 |
|---|---|---|
| 回答 | **我会什么** | 我是谁 |
| 内容 | 技术方案、踩坑、语法、方法 | 性格、经历、关系、决策 |
| 检索 | 按关键词找知识 | 按话题找上下文 |
| 可见性 | 可能分享/公开 | **永远私有** |

**判据**：如果一条内容的价值来自"**它**"（这个方案为什么可行），进知识库；
如果价值来自"**你**"（我当时的处境和选择），进个人档案。
两者都可以记，但**放在不同的地方**，不要互相引用。
